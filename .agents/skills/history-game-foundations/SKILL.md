# History Game Foundations

역사수업용 게임에서는 **학습 목표 > 플레이 흐름 > 시각적 연출** 순으로 판단한다.

보고와 작업 메모는 사용자가 다른 언어를 요구하지 않는 한 한국어로 작성한다.

## 1. 저장소 우선 원칙

이 스킬의 예시는 권장 패턴이지 마이그레이션 지시가 아니다. 작업 전에 현재 저장소를 먼저 읽고 다음을 확인한다.

- 현재 배포 방식(GitHub Pages, GAS, 서버, 기타)
- 현재 파일 구조(단일 HTML, 다중 파일, 프레임워크)
- 주 입력 장치(터치, 키보드/트랙패드, 혼합)
- 현재 저장 방식(Supabase, 서버 API, localStorage 등)
- 기존 `AGENTS.md`, 테스트, 디자인 규칙

**기존 구조가 동작하고 있으면 보존한다.** 특히 단일 HTML 게임을 새 프레임워크나 다중 파일 구조로 쪼개지 않는다. 사용자가 명시적으로 리팩터링을 요청했거나, 현재 구조로는 요구사항을 안전하게 구현할 수 없는 경우에만 구조 변경을 제안한다.

## 2. 기본 수업 가정

저장소에 별도 정보가 없을 때만 다음을 임시 기본값으로 사용한다.

- 고등학생, 사전지식이 많지 않음
- 개인 활동
- 50분 한 차시
- 브라우저 기반, 빠른 첫 진입
- 핵심 조작은 2~4개의 반복 동사로 제한

기기 가정은 고정하지 않는다. 저장소/AGENTS.md에서 `touch-first`, `keyboard-first`, `mixed` 중 하나를 우선한다.

## 3. 핵심 질문

모든 장면은 다음 질문에 답해야 한다.

> 학생이 이 장면에서 하는 행동이 어떤 역사적 사고를 요구하는가?

다음과 연결되지 않는 조작은 줄이거나 제거한다.

- 관찰
- 비교
- 연결
- 원인/결과 추론
- 사료 신뢰도 판단
- 증거 선택
- 역사적 판정
- 판정 수정

## 4. 현재 구조를 유지한 관심사 분리

파일을 반드시 나누라는 뜻이 아니다. 단일 HTML에서도 아래 관심사를 코드 블록/객체/함수 수준에서 분리한다.

1. **역사 콘텐츠** — 사료, 날짜, 행위자, 장소, 출처, 교사용 주석
2. **결정적 게임 규칙** — 상태 전이, 선택, 증거 획득, 판정, 엔딩
3. **표현** — DOM, Canvas/Phaser, 오디오, 애니메이션
4. **저장/검증** — 세션, 제출, 저장, 분기 검사, 스모크 테스트

역사적 사실을 클릭 핸들러나 렌더링 코드에 숨기지 않는다.

## 5. DOM / Canvas 경계

DOM이 적합한 것:
- 긴 한국어 텍스트
- 사료 설명·출처
- 증거 카드
- 선택지
- 입력/논술
- 접근성에 민감한 UI

Canvas/Phaser가 적합한 것:
- 공간 이동
- 카메라 이동
- 스프라이트 상호작용
- 공간 탐색 자체가 의미 있는 장면

일반 문서 UI를 Canvas 안에 재구현하지 않는다.

## 6. 상태와 저장

직렬화 가능한 하나의 상태를 기준으로 삼는다. DOM 노드, Phaser 객체, 함수, 타이머, 오디오 객체는 저장하지 않는다.

예:
```js
{
  sessionId,
  sceneId,
  completedMissions: [],
  evidenceIds: [],
  judgments: {},
  flags: {},
  history: [],
  version: 1
}
```

### 저장 우선순위

1. 저장소에 이미 있는 백엔드/제출 인프라(Supabase 등)를 우선 사용한다.
2. 기존 저장 추상화가 있으면 그것을 확장한다.
3. localStorage는 임시 진행 캐시나 오프라인 보조 수단으로만 추가한다. 기존 영구 저장을 대체하지 않는다.

### 공용/순환 기기

공용 기기를 여러 학생/반이 돌려쓰는 프로젝트라면:
- 기본 진입은 **새로 시작**;
- 이어하기는 명시적 선택;
- 사용자/세션이 바뀌면 이전 로컬 상태를 자동 복원하지 않음;
- 제출 성공 또는 세션 종료 후 민감하거나 학생별인 로컬 진행 데이터는 정리;
- 서버 제출 데이터와 로컬 캐시를 동일한 것으로 취급하지 않음.

### 백엔드 보안(Supabase 등)

- `service_role`/secret 키는 클라이언트 코드에 절대 넣지 않는다. 쓰기 권한이 필요하면 RLS 정책이나 서버 함수로 해결한다.
- 브라우저에는 anon/publishable 키만 사용하고, 대상 테이블의 RLS 활성화 여부를 확인한다.
- 학생 이름·학번 등 식별 정보를 localStorage, 콘솔 로그, 테스트 fixture, 커밋에 남기지 않는다.

## 7. 역사적 정확성과 해석 범위

- 실제 인용처럼 보이는 문장을 창작하지 않는다.
- 사실/사료 필드는 저장소 내 출처 데이터와 연결한다.
- `historicalFact`, `sourceEvidence`, `gameFiction` 또는 동등한 구분을 유지한다.
- 연대 압축·합성 인물·극적 연결 대사는 교사/개발자 주석에서 표시한다.

### 닫힌 사실과 열린 추론을 구분한다

수업 자료와 신뢰할 수 있는 출처로 확인되는 날짜, 문서 내용, 작성자, 사건 발생 여부 같은 **확정 사실**을 서로 동등한 선택지처럼 열어두지 않는다.

학생에게 열어둘 것은 주로:
- 어떤 증거를 더 중요하게 볼지;
- 사료의 한계와 신뢰도를 어떻게 판단할지;
- 원인·영향의 비중을 어떻게 설명할지;
- 근거를 어떻게 연결해 판정을 방어할지.

쟁점성이 있는 주제는 저장소에 제공된 수업 자료와 출처를 기준으로 사실과 입장을 구분하고, 출처가 없는 주장을 임의로 확정하지 않는다.

## 8. 역사 검증 프로토콜

'검증함'이라고만 보고하지 않는다.

1. 저장소의 사료 데이터, 교과서 발췌, 출처 메모, citation 필드를 찾는다.
2. 해당 주장과 직접 대조한다.
3. 근거 파일/필드/라인 또는 데이터 ID를 결과에 기록한다.
4. 저장소 안에 확인 근거가 없고 외부 검증도 허용/가능하지 않으면 다음 표시를 남긴다.

`UNVERIFIED – 교사 확인`

검증되지 않은 내용을 사실 확정형 문장으로 새로 추가하지 않는다.

## 9. 50분 시간 예산

기본 계획 예시는 합계가 50분을 넘지 않게 잡는다.

- 진입/조작 안내: 최대 3분
- 핵심 플레이: 최대 32분
- 최종 판정/산출물: 최대 7분
- 지연·재시도·교사 마무리 여유: 최소 8분

장면 하나는 보통 3~7분 안에서 끝나도록 한다. 첫 의미 있는 행동 전에 긴 설명을 두지 않는다.

## 10. 메커닉 예산

새 메커닉을 추가하기 전 기존 동사로 표현 가능한지 확인한다.

권장 반복 동사:
- 살펴보기
- 비교하기
- 배열/분류하기
- 연결하기
- 선택하기
- 판정 수정하기
- 이동/상호작용하기

50분 게임 하나에 비주얼노벨 + 자유 이동 + 퍼즐 보드 + 관계망 + 드래그앤드롭 + 타임라인 + 미니게임을 모두 넣지 않는다.

## 완료 기준

- 첫 사용자에게 교사의 즉시 구조 없이 시작 가능
- 기존 저장소 구조를 불필요하게 변경하지 않음
- 필수 사료/장면 도달 가능
- 저장/제출 경로가 기존 인프라와 충돌하지 않음
- 공용 기기에서 이전 사용자의 진행을 자동 승계하지 않음
- 주 입력 장치에서 핵심 조작 가능
- 최종 활동이 단순 완주가 아니라 역사적 판단·설명·증거 사용을 요구
- 중요한 역사 주장에는 저장소 근거 또는 `UNVERIFIED – 교사 확인` 표시가 있음
