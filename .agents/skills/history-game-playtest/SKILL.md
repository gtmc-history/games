# History Game Playtest

세 가지를 동시에 검수한다.
1. 소프트웨어
2. 게임 흐름
3. 역사 학습 과제

기술 테스트 통과만으로 수업 투입 가능 판정을 내리지 않는다. 보고는 기본적으로 한국어로 한다.

## 0. 저장소 프로필 확인

먼저 확인한다.
- 현재 구조(단일 HTML/다중 파일/프레임워크)
- 실제 배포 방식
- 주 입력 장치
- 실제 저장/제출 방식(Supabase 포함)
- 기존 테스트/검수 스크립트
- 저장소 내 사료 근거

검수 과정에서 새 프레임워크나 대규모 리팩터링을 시작하지 않는다.

## 1. 정적/데이터 검사

- build/lint/typecheck가 있으면 실행
- 누락 asset
- 중복 ID
- 깨진 분기 참조
- 선택지 없는 비종료 노드
- 도달 불가능한 필수 장면/엔딩
- 종료로 빠져나갈 수 없는 루프
- 획득 불가능한 필수 증거
- 저장 데이터 버전/손상 처리

분기 JSON 또는 `branch-data` 단일 HTML이 호환되면:
```bash
node .agents/skills/historical-narrative-branching/scripts/validate-branch-graph.mjs path/to/game.json
```

## 2. 결정적 엔진 검사

UI 없이 가능한 범위를 테스트한다.
- 시작 상태
- 대표 선택
- 증거 획득
- 판정 수정
- 엔딩
- 새로 시작
- 이어하기
- 제출 후 상태

## 3. 경로 검사

작은 게임은 가능한 경로를 전수 또는 준전수 검사한다.
큰 게임은 최소한:
- 최단 경로
- 가장 긴 현실적 경로
- 각 엔딩
- 각 필수 사료
- 뒤로가기/중복 상호작용
- 중단/새로고침
- 이미 완료한 미션 재진입

## 4. 저장·제출·공용 기기

기존 백엔드가 있으면 실제 통합 경로를 확인한다.

- 서버 제출 성공/실패 처리
- 중복 제출 방지 또는 의도된 허용
- 네트워크 실패 후 복구
- localStorage와 서버 상태 충돌
- 다음 학생이 열었을 때 이전 학생 진행 자동 복원 여부
- 기본 진입이 새 세션인지
- 이어하기가 명시적인지
- 제출/종료 후 로컬 학생 상태 정리 여부

- 클라이언트 코드에 `service_role`/secret 키가 없는지 검색 (발견 시 BLOCKER)
- 대상 테이블 RLS 활성화 여부 (확인 불가 시 `UNVERIFIED – 교사 확인`)
- 학생 식별 정보가 localStorage·콘솔 로그에 남지 않는지

Supabase를 쓰는 저장소에서 localStorage 테스트만 하고 '저장 PASS'라고 판정하지 않는다.

## 5. 브라우저 스모크

프로젝트가 실제로 사용하는 기기를 기준으로 한다.

공통:
- fresh start
- reload
- 긴 한국어 줄바꿈
- 오디오 사용자 제스처 제한
- 모달/오버레이 후 입력 복귀
- 브라우저 뒤로가기/새로고침 위험

`touch-first`라면:
- 핵심 경로 터치만으로 완주
- hover 필수 요소 없음
- 작은 타깃 없음

`keyboard-first`라면:
- 키보드/트랙패드 핵심 경로
- 입력창 포커스 중 게임 단축키 오작동 없음

Canvas/Phaser는 DOM assertion만으로 끝내지 말고 실제 화면/스크린샷을 확인한다.

## 6. 첫 사용자 검사

사전지식이 적은 학생으로 플레이한다. 다음 순간을 기록한다.
- 설명되지 않은 역사 지식이 필요함
- 교사 개입이 필요함
- UI 의미를 추측해야 함
- 행동 전에 긴 글을 읽어야 함
- 기록할 수 없었던 정보를 기억해야 함
- 실패 후 복구 방법이 없음

## 7. 역사 QA

'사실 검증 완료'를 추정으로 선언하지 않는다.

각 핵심 주장/사료마다:
1. 저장소 내 근거 파일/데이터를 찾음
2. 날짜·행위자·문서 내용·인용/의역을 직접 대조
3. 검수 결과에 근거 위치를 기록
4. 근거가 없으면 `UNVERIFIED – 교사 확인`

확정 사실과 학생에게 허용할 해석 범위를 구분한다. 극적 대사를 사료 근거로 취급하지 않는다.

## 심각도

- **BLOCKER**: 완주 불가, 데이터 손실/오제출, 역사적 오정보 가능성이 큼
- **HIGH**: 주요 분기/사료/저장/입력 실패, 많은 학생이 막힘
- **MEDIUM**: 혼란, 약한 피드백, 시간 초과 위험, 중요한 시각 결함
- **LOW**: 완주/학습에 작은 영향의 다듬기

새 기능보다 BLOCKER/HIGH를 먼저 고친다.

## 수업 투입 게이트

분기 검사기가 `CONDITIONAL PASS`를 내면 수동/브라우저 경로 검사가 끝나기 전에는 전체 수업 투입 판정을 PASS로 올리지 않는다.

PASS 조건:
- 알려진 BLOCKER/HIGH 없음
- 첫 사용자 진입이 약 60초 안에 가능
- 필수 경로가 수업 시간 내 여유 포함 완료
- 잘못된 상호작용에서 회복 가능
- 최종 산출물 수집/검토 가능
- 실제 저장/제출 경로 검증
- 공용 기기라면 이전 사용자의 진행이 자동 승계되지 않음
- 핵심 역사 주장 검증 또는 명시적 UNVERIFIED 표시

## 보고 형식

1. `PASS / CONDITIONAL PASS / NO-GO`
2. BLOCKER/HIGH부터
3. 실행한 테스트와 관찰 증거
4. 역사 검증 근거 또는 `UNVERIFIED – 교사 확인`
5. 정확한 파일/영역
6. 최소 수정안
7. 재실행할 회귀 테스트
